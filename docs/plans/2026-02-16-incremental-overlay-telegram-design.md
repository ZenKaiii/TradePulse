# TradePulse 增量推送与专题命中修复设计

## 背景与问题
- A部分重复输出：当前流水线虽然统计 `new_events`，但推送正文始终使用 `top_events`，未按 ledger 过滤真正“新增”。
- A部分质量偏低：排序仅依赖规则分，缺少发布时间约束与来源去偏置，导致老旧/同源新闻反复进入 Top10。
- B部分命中不准：专题匹配只在 Top10 标题文本上做简单子串；股票/地缘存在明显误匹配（如 `MU` 命中 `community`，`us-china-tech` 因 `us` 高频而常驻命中）。
- Telegram 无输出：`TRADEPULSE_CHANNELS` 为空时回退到 `delivery.channels` 默认值（仅 dingtalk），即使 Telegram 密钥已配置也不会发送。

## 目标
1. 真正增量推送：同一 cluster 不重复出现在 A 区域。
2. 提升 A 区域质量：加入新鲜度与来源上限，减少单源刷屏。
3. 修复 B 区域匹配：从“Top10标题子串”升级为“全候选事件+正则边界+命中条目”。
4. Telegram 自动启用：当 channels 未显式配置时，按可用密钥自动选择通道。
5. C 区域增强：增加“板块轮动候选观察清单（非投资建议）”，把板块强弱转成可执行观察步骤。

## 方案对比
### 方案1：最小修补（仅修 channels 和 overlay 规则）
- 优点：改动小，风险低。
- 缺点：A 重复与低质量问题仍在，无法满足“增量推送”核心诉求。

### 方案2：流水线重构（推荐）
- 做法：在排序后引入“新鲜度+来源上限+ledger 增量筛选”；overlay 升级为结构化命中；通道改自动探测；C区增加候选清单。
- 优点：一次性解决三类用户痛点，且保持现有模块边界。
- 缺点：需要补测试并改文档。

### 方案3：引入外部队列/数据库持久层
- 优点：可做更复杂状态管理。
- 缺点：超出当前 GitHub Actions 轻量部署目标，YAGNI。

## 设计决策
- 采用方案2。
- 增量策略：A区默认只显示本轮“未推送过”的事件；若无新增则显示“本小时无新增关键事件”。
- 新鲜度策略：新增 `digest.max_age_hours`（默认 72），过滤过旧事件；解析失败的发布时间不直接丢弃，但降低排序优先级。
- 来源去偏置：新增 `digest.max_per_source`（默认 3），限制同一 source 在 A区的占比。
- 专题命中：
  - 股票：ticker 使用单词边界匹配（支持 `$NVDA`/`NVDA`），避免子串误命中。
  - 关键词：大小写不敏感短语匹配。
  - 地缘：主题分词后要求“至少命中2个 token（或全部可用 token）”，避免 `us` 单词单独触发。
  - 输出带命中条目（标题+来源，限3条）。
- 通道选择：新增 `resolve_channels()`。
  - 若 env `TRADEPULSE_CHANNELS` 非空：严格按显式配置。
  - 否则按可用密钥自动启用（dingtalk/telegram/feishu）。
- C区增强：新增“轮动候选观察”段落：
  - 基于领先板块映射代表股，给出观察清单与入场检查项（周线基座、日线收紧、均线状态），明确“非投资建议”。

## 风险与缓解
- 风险：增量后“无新增”频率变高。
- 缓解：正文显式提示“无新增”并保留 B/C 作为监控信息。
- 风险：更严格专题匹配导致命中减少。
- 缓解：在 README 增加配置示例（ticker/关键词/地缘主题写法）。

## 验证策略
- 单测覆盖：
  - ledger 增量过滤行为。
  - overlay 边界匹配与命中详情。
  - auto channel 对 Telegram 场景生效。
  - C区候选观察段落渲染。
- GitHub Actions 日志验证：
  - `new_events` 与 A区条目一致。
  - 已配置 Telegram 时发送器数量>0。
